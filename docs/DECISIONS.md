# OpenBar — Architectural Decision Records (ADR)

## ADR-0001: Clean Architecture modular solution structure
- **Date:** 2026-11-16
- **Status:** Accepted
- **Context:** OpenBar must evolve into a full desktop product (dock, widgets, system bridge, integrations, automation) with maintainability and extensibility.
- **Decision:** Use Clean Architecture layers/projects (`Domain`, `Application`, `Infrastructure`, `Presentation`, `App`) plus dedicated modules (`Dock`, `WidgetRuntime`, `Widgets.Abstractions`, `Integrations`, `Automation`) and per-domain widget module folders under `modules/`.
- **Consequences:** Clear boundaries and testability; requires discipline to keep dependencies directional and avoid leaky abstractions.

## ADR-0002: Independent WinUI dock window (no taskbar/Explorer replacement)
- **Date:** 2026-11-16
- **Status:** Accepted
- **Context:** Modifying Explorer/taskbar is risky and destructive; product must be stable and lightweight.
- **Decision:** Implement dock as an independent window using WinUI 3 / Windows App SDK and Windows APIs as needed; do not remove or destructively modify Explorer or the original taskbar.
- **Consequences:** Safer integration path; some shell integrations may require additional Win32 interop later.

## ADR-0003: Widget extensibility and plugin isolation
- **Date:** 2026-11-16
- **Status:** Accepted — Foundation 0.3 implements the in-process runtime; out-of-process plugins remain future work.
- **Context:** Widgets must be extensible without core changes; third-party code cannot be trusted.
- **Decision:** Define `IWidget`/`WidgetDefinition` contracts and a runtime for registration/lifecycle/scheduling/error isolation. Official widgets run in-process; third-party plugins run out-of-process with IPC. `AssemblyLoadContext` is not considered a security boundary.
- **Consequences:** Stronger safety for plugins at the cost of IPC/hosting complexity (deferred beyond the initial foundation).

## ADR-0004: Centralized System Bridge and shared scheduler
- **Date:** 2026-11-16
- **Status:** Accepted
- **Context:** Multiple widgets/features need system metrics; naive polling wastes resources and can block UI.
- **Decision:** Centralize Windows/system access behind shared services with a scheduler/cache and event-driven updates where possible; handle sensor/driver limitations gracefully.
- **Consequences:** Lower overhead and consistent data; requires careful lifetime and throttling design.

## ADR-0005: Persistence and secrets handling
- **Date:** 2026-11-16
- **Status:** Accepted — **implemented in Foundation 0.2** (see ADR-0014 to ADR-0021)
- **Context:** App state must persist; credentials must be protected.
- **Decision:** Use SQLite + EF Core for app data (widgets/config/layouts/themes/integrations config/automations/preferences) with controlled migrations. Store tokens/credentials only in Windows Credential Manager or DPAPI, never in plaintext or DB.
- **Consequences:** Local, portable state; requires secure key management abstractions.

## ADR-0006: Target stack and environment verification gate
- **Date:** 2026-11-16 (updated same day after revalidation)
- **Status:** **Verified (closed 2026-11-16)** — .NET 10 SDK installed
- **Context:** Requested stack specifies C# 14, .NET 10 LTS, WinUI 3, Windows App SDK 2.6.5, Windows SDK 26100. Initial revalidation found only SDK 11.0.100 (no 10.x) with `global.json` pinning 10.0.100, which blocked restore. Later the same day, SDK **10.0.404** was installed alongside 11.0.100; `global.json` (`rollForward: latestFeature`) resolved to 10.0.404.
- **Decision:** Keep target framework on .NET 10 and the `global.json` intent; do not retarget to .NET 11. Verified the stack by actual restore/build/test/run instead of assumptions.
- **Consequences:** `dotnet restore`, `build` (0 warnings, 0 errors), `test` (4/4 at that Foundation 0.1 snapshot; **114/114 after Foundation 0.2; 186/186 after Foundation 0.3; 230/230 after Foundation 0.4; 238/238 after Foundation 0.5**) and app launch all succeeded on SDK 10.0.404 with Windows App SDK 2.6.5. Remaining Foundation 0.1 work is feature work, not environment work.

## ADR-0007: CLI builds default to x64; use a canonical, restorable solution file
- **Date:** 2026-11-16
- **Status:** Accepted
- **Context:** The hand-authored `OpenBar.sln` lacked `ProjectConfigurationPlatforms` entries, so `dotnet restore OpenBar.sln` reported “No project found to restore”. Separately, `OpenBar.App` uses `WindowsAppSDKSelfContained=true`, which errors when the platform resolves to AnyCPU.
- **Decision:** Maintain a canonical `OpenBar.sln` generated by `dotnet new sln --format sln` + `dotnet sln add` (14 projects at the time; 16 after Foundation 0.3 added the clock module and runtime tests; 17 after Foundation 0.4 added the dock tests). `Directory.Build.props` defaults `Platform`/`PlatformTarget` to `x64` when no explicit platform is supplied, while `Platforms` still declares ARM64/x86.
- **Consequences:** Plain `dotnet restore/build/test OpenBar.sln` works. x64 is the validated baseline; ARM64/x86 are declared but unverified.

## ADR-0008: Pin the patched SQLitePCLRaw 2.1.x bundle
- **Date:** 2026-11-16
- **Status:** Accepted
- **Context:** EF Core Sqlite 10.0.0 pulls `SQLitePCLRaw.lib.e_sqlite3` 2.1.11, flagged high-severity by GHSA-2m69-gcr7-jv3q (CVE-2025-6965). A central `PackageVersion` alone does not move a transitive-only package.
- **Decision:** Add a direct `PackageReference` to `SQLitePCLRaw.bundle_e_sqlite3` in `OpenBar.Infrastructure`, centrally pinned to **2.1.14** (patched 2.1.x line). Do not jump to the 3.x family yet because it changes assembly identity/major line; revisit when EF Core itself raises the floor.
- **Consequences:** NU1903 disappears, `dotnet list package --vulnerable --include-transitive` is clean, and a runtime test asserts SQLite ≥ 3.50.2. The pin must be re-evaluated on EF Core upgrades.

## ADR-0009: Windows SDK BuildTools version follows Windows App SDK requirement

## ADR-0010: Single instance via unowned named mutex plus per-user named-pipe activation
- **Date:** 2026-11-16
- **Status:** Accepted
- **Context:** OpenBar must never run two primary instances. A second launch has to bring the existing instance forward and exit. Mutex ownership (`WaitOne`) ties release to a specific thread, which complicates shutdown on the WinUI dispatcher and needs abandoned-mutex handling after a crash.
- **Decision:**
  - Create a named mutex with `initiallyOwned: false` purely as a kernel object marker: the first process creates it (`createdNew == true`) and keeps the handle open; others observe `createdNew == false`.
  - Do not call `WaitOne`/`ReleaseMutex`. A crashed process releases the name when Windows closes its handles, so stale locks cannot block future launches.
  - Activation uses a per-user named pipe (`<appId>.SingleInstance.<userSID>`, `PipeOptions.CurrentUserOnly`). The primary runs a `NamedPipeServerStream` listener as an `IHostedService`; the second process connects and writes a one-byte activation request, then exits.
  - Scope both names by the current user SID so different Windows users never collide.
- **Consequences:** No thread affinity on shutdown, crash-safe, and no need to discover or message a foreign HWND. Activation is asynchronous and marshalled to the UI thread. A prior instance that exits between the mutex check and the pipe connect is handled by one re-acquisition attempt in `App`. IPC contract: a single `0x01` byte means "activate"; it is intentionally minimal and versionless for now.

## ADR-0011: System tray implemented with `Shell_NotifyIcon` on a hidden top-level window
- **Date:** 2026-11-16
- **Status:** Accepted
- **Context:** The tray icon must exist without WinForms (`NotifyIcon`) or extra packages, must receive shell callbacks (`WM_*` notifications, `TaskbarCreated` after Explorer restarts) and must not affect process lifetime.
- **Decision:**
  - Implement `WindowsSystemTrayService` in `OpenBar.Infrastructure` with direct `Shell_NotifyIcon` / `NOTIFYICONDATA` / `LoadImage` / `TrackPopupMenuEx` P/Invoke.
  - Host the icon on a hidden **top-level** Win32 window with a per-instance generated class name. Message-only windows are rejected because they do not receive the `TaskbarCreated` broadcast.
  - Keep `StartAsync`/`StopAsync` synchronous so window creation/destruction runs on the UI thread that owns the WinUI message loop; `Dispose` refuses a cross-thread `DestroyWindow`.
  - Map tray commands through the platform-neutral `TrayCommandController` (Application) so behavior is unit-testable.
  - Do not post `WM_QUIT` from the tray window; the WinUI dispatcher owns process lifetime.
- **Consequences:** No WinForms dependency and full shell callback support. The service must be documented as UI-thread-affine. Tray creation failures are logged and never block the dock from opening.

## ADR-0012: Lifecycle state machine and UI-thread shutdown orchestration
- **Date:** 2026-11-16
- **Status:** Accepted
- **Context:** Multiple sources (tray, future commands, second-instance handling) can request shutdown, and the window's close button must not terminate the process. Host stop and window close must run in a defined order on the correct thread.
- **Decision:**
  - `ApplicationLifecycleService` (Application) is the single, thread-safe, idempotent shutdown coordinator (`Starting → Running → ShuttingDown → Stopped`). The first `RequestShutdown(reason)` wins; later requests are ignored, and handler failures are logged without aborting shutdown.
  - `DockWindowService` centralizes window policy: the X button cancels the close and hides; minimize hides to tray; only `CloseForShutdown()` (after `IsShuttingDown`) really closes.
  - Shutdown order: stop the host (tray icon removed and tray window destroyed on the UI thread) → marshal completion to the dispatcher → close the window → mark lifecycle stopped → dispose the host → `Exit()`.
  - The Host is built once; hosted services start in registration order and stop in reverse order.
- **Consequences:** Deterministic, idempotent shutdown and no duplicate window/tray teardown. Closing the window keeps the process alive by design; exiting is only possible through the tray (or a future explicit command).

## ADR-0013: Provisional project-owned application/tray icon
- **Date:** 2026-11-16
- **Status:** Accepted (provisional asset)
- **Context:** Windows requires a stable `.ico` for the executable and the tray. The repository had no icon; external icon assets/licenses were not available.
- **Decision:** Generate a project-owned multi-size `.ico` (`src/OpenBar.App/Assets/OpenBar.ico`, 16/24/32/48/256 px PNG entries) with a simple rounded glass-dock motif. Reference it as `<ApplicationIcon>` and copy it to the output `Assets` folder for `LoadImage`.
- **Consequences:** The app and tray have a consistent icon with no third-party licensing. **The icon is provisional placeholder art** and must be replaced by the final brand artwork before release. `LoadImage` falls back to the system application icon if the file is missing, and logs a warning.

## ADR-0014: Database lives in `%LOCALAPPDATA%` and schema changes are migration-only
- **Date:** 2026-11-16
- **Status:** Accepted
- **Context:** Configuration must survive restarts and upgrades, but must never be written into the repository, the build output or the installation folder. Creating schema implicitly hides upgrade failures.
- **Decision:**
  - Resolve the database directory from `Environment.SpecialFolder.LocalApplicationData`, i.e. `%LOCALAPPDATA%\OpenBar\openbar.db`, and create the folder automatically. No hard-coded user paths.
  - Centralize location, file name, busy timeout, lock timeout, WAL flag, pooling and backup retention in `OpenBarDatabaseOptions`; tests override only `DirectoryPath`.
  - Use EF Core migrations exclusively. `EnsureCreated()` is forbidden. `PersistenceStartupService` applies pending migrations at startup.
- **Consequences:** State is per-user and portable across app upgrades; tests run against isolated temp databases. A schema change always requires a reviewed migration.

## ADR-0015: SQLite connection pragmas, WAL and pooling discipline
- **Date:** 2026-11-16
- **Status:** Accepted
- **Context:** SQLite defaults vary per connection: foreign keys are off unless enabled, the default busy timeout is short, and rollback journals hurt concurrent readers.
- **Decision:**
  - Build the connection string once in `SqliteConnectionStringFactory` (`ReadWriteCreate`, foreign keys on, default timeout derived from the busy timeout, pooling controlled by options).
  - Apply `PRAGMA foreign_keys = ON` and `PRAGMA busy_timeout` through a `DbConnectionInterceptor` so every connection gets them, including ones opened by EF Core.
  - After initialization switch the database to WAL (`synchronous = NORMAL`).
  - Keep contexts short-lived through `IDbContextFactory<OpenBarDbContext>`; never share a context across concurrent operations. `StopAsync` calls `SqliteConnection.ClearAllPools()` so no handle survives shutdown.
- **Consequences:** Predictable integrity and concurrency behavior. WAL leaves `-wal`/`-shm` sidecars next to the database; that is normal and must not be mistaken for corruption. Pooling must be disabled in tests that delete their temp folder unless the pool is explicitly cleared.

## ADR-0016: Pre-migration backup, integrity check and non-destructive corrupt-database quarantine
- **Date:** 2026-11-16
- **Status:** Accepted
- **Context:** A failed upgrade or a corrupt file must never destroy a user's configuration. Silently recreating the database is data loss.
- **Decision:**
  - Run `PRAGMA quick_check` on an existing non-empty database before touching it.
  - When migrations are pending, take an online backup into `backups/` (retention: 5) **before** applying anything.
  - If the database is corrupt, move the original file and its `-wal`/`-shm`/`-journal` sidecars into `backups/corrupt/` byte-for-byte, then create a fresh database. Attempt recovery once.
  - If a migration fails, stop startup with a controlled exception. Never delete, downgrade or rewrite user data.
- **Consequences:** Upgrades are recoverable and corrupt files are retained for diagnosis. Disk usage grows with backups, bounded by retention. Startup can fail loudly after a migration error, which is preferred over silent data loss.

## ADR-0017: Serialize database initialization in-process and across processes
- **Date:** 2026-11-16
- **Status:** Accepted
- **Context:** EF Core's `__EFMigrationsLock` prevents concurrent migration application, but the surrounding steps (integrity check, backup, data load) need protection too, and two OpenBar processes must never initialize simultaneously.
- **Decision:**
  - Guard initialization with an in-process `SemaphoreSlim` plus a cached successful result, so repeated calls are cheap and single-flight.
  - Use an exclusive lock file (`openbar.db.migration.lock`, `FileShare.None`, `DeleteOnClose`) with a bounded wait so a second process either waits or fails with a controlled `DatabaseInitializationException`.
  - Run the whole sequence from a hosted service on a worker thread (`Task.Run`), honoring the `CancellationToken` passed by the host.
- **Consequences:** No double migration or UI-thread blocking. A crashed process releases the OS file handle, so stale locks do not persist. The lock file is diagnostic only and must not survive a clean exit (tests assert this).

## ADR-0018: `AppSetting` is the single global preference store; secrets are rejected
- **Date:** 2026-11-16
- **Status:** Accepted
- **Context:** The persistence model requested an optional `UserPreference` entity. Adding it alongside `AppSetting` would create two competing mechanisms for the same kind of data. Separately, it is easy to accidentally persist a token as a "setting".
- **Decision:**
  - Use `AppSettings` for global, non-secret key/value preferences. Do not add a `UserPreference` table; per-widget configuration belongs to `WidgetInstances.SettingsJson`, and dock geometry belongs to `DockLayouts`.
  - Enforce `SettingKeyPolicy` (rejects `password`, `passwd`, `secret`, `token`, `apikey`/`api_key`, `privatekey`/`private_key`, `credential`) in the settings service before any write.
  - Keep credentials out of SQLite entirely; a Credential Manager/DPAPI abstraction will be introduced in a later phase. Nothing sensitive is logged.
- **Consequences:** One predictable preference pipeline and a defensive boundary against secret leakage. The key policy is a guard, not encryption; real secret storage remains pending work.

## ADR-0019: Layouts store logical monitor selectors, never hardware IDs
- **Date:** 2026-11-16
- **Status:** Accepted
- **Context:** Monitor device paths and EDIDs change across docks, driver updates and reconnections, so persisting them makes layouts unstable.
- **Decision:** `DockLayouts.MonitorTarget` stores a logical selector such as `primary` or `index:N`. Resolution against the current monitor topology happens at runtime.
- **Consequences:** Layouts survive monitor reordering and hardware changes. A layout may resolve to a different physical monitor if the topology changed; that is acceptable and preferred over invalid persisted hardware references.

## ADR-0020: Focused persistence services over a generic repository; `IDbContextFactory` instead of a scoped context
- **Date:** 2026-11-16
- **Status:** Accepted
- **Context:** A generic repository would hide EF Core query semantics and encourage leaky, lowest-common-denominator APIs. A single long-lived `DbContext` is not thread-safe and would serialize unrelated work.
- **Decision:**
  - Put ports in `OpenBar.Application/Persistence` (`IAppSettingsService`, `IWidgetInstanceService`, `IDockLayoutService`, `IDatabaseInitializer`) and implement them in `OpenBar.Infrastructure/Persistence`.
  - Create one short-lived `OpenBarDbContext` per operation from a singleton `IDbContextFactory`. No `AddDbContext` scoped context, no shared context.
  - Wrap multi-row changes (`SetManyAsync`, `SaveManyAsync`, `SetDefaultAsync`) in explicit transactions; let single-row operations rely on `SaveChangesAsync`.
  - Translate provider failures into `PersistenceValidationException` / `PersistenceConflictException` / `PersistenceNotFoundException` without leaking SQL or stored values.
- **Consequences:** Queries stay explicit and index-friendly, services are independently testable, and concurrency is safe by construction. Each new use case adds a focused method instead of a generic CRUD surface.

## ADR-0021: Keep EF Core design-time tooling outside the production solution
- **Date:** 2026-11-16
- **Status:** Accepted
- **Context:** `Microsoft.EntityFrameworkCore.Design` is required to scaffold migrations, but it brings build-time dependencies that would surface vulnerability warnings in the production dependency graph (NU1903) without benefiting the shipped app.
- **Decision:**
  - Add `tools/OpenBar.DesignTime`, a self-contained `win-x64` executable referencing `OpenBar.Infrastructure` and `Microsoft.EntityFrameworkCore.Design` (`PrivateAssets=all`), and keep it out of `OpenBar.sln`.
  - Pin `dotnet-ef` **10.0.0** as a local tool in the repository-root `dotnet-tools.json` (`rollForward: false`).
  - Generate migrations with `--startup-project tools/OpenBar.DesignTime`.
- **Consequences:** The app build stays warning-free and the migration workflow is reproducible. The design-time project must be updated when the EF Core runtime version changes; it is intentionally not built by `dotnet build OpenBar.sln`.

## ADR-0022: Initialize the git repository with a .NET/WinUI `.gitignore`, without automatic commits
- **Date:** 2026-11-16
- **Status:** Accepted
- **Context:** The workspace had no version control, which makes staged changes and reviews impossible. Committing automatically would take control away from the user.
- **Decision:** Initialize a repository, add a `.gitignore` covering `bin/`, `obj/`, IDE state, local databases/backups, logs, secrets and MSIX output, and leave all Foundation 0.2 changes uncommitted.
- **Consequences:** Changes are reviewable with `git status`/`git diff`; the user decides when and how to commit. Generated databases and backups are never tracked.

## ADR-0023: Stable widget ids and a UI-free contract assembly
- **Date:** 2026-11-16
- **Status:** Accepted
- **Context:** Widgets need a stable identity independent of display names, file names and physical assemblies. The runtime must not depend on WinUI, and widgets must not receive the application DI container or database.
- **Decision:**
  - `WidgetDefinition.WidgetId` is a required lower-case logical id (letters/digits/dots/underscores/hyphens), validated by `WidgetDefinitionValidator`.
  - Contracts live in `OpenBar.Widgets.Abstractions`: `WidgetDefinition`, `WidgetMetadata`, `IWidget`, `WidgetContext`, `WidgetSettings`, `IWidgetScheduler`, `IWidgetSettingsConsumer`, `WidgetBase`.
  - `WidgetContext` exposes only the instance identity, validated settings, an `ILogger` and an instance-scoped scheduler. The raw `IServiceProvider` is not exposed.
  - `IWidget.CreateView()` returns `object` (a `Microsoft.UI.Xaml.UIElement` in the WinUI host), keeping the contract usable by a future out-of-process host.
- **Consequences:** Widgets are decoupled from persistence and windowing; the runtime can be tested without WinUI. The opaque view object is a deliberate trade-off until a serialized view contract exists.

## ADR-0024: Separate definition registry from user instances; tolerant discovery
- **Date:** 2026-11-16
- **Status:** Accepted
- **Context:** A catalog entry and a user's saved instance are different concepts. A broken module must not hide the rest of the catalog, and an unavailable widget must not cause its configuration to be deleted.
- **Decision:**
  - `WidgetRegistry` holds definitions only; `WidgetInstances` rows remain in SQLite.
  - `IWidgetDefinitionProvider` supplies definitions; `ConfiguredWidgetDefinitionProvider` exposes the official definitions registered in DI.
  - `WidgetDiscoveryService` catches failures per provider and per definition and returns `WidgetDiscoveryResult` with failures.
  - Persisted instances without a definition are reported as `Unavailable` and preserved.
- **Consequences:** A partial catalog is usable and diagnosable. Discovery is not a dynamic plugin loader; adding one later means adding a provider.

## ADR-0025: Explicit widget state machine with per-instance serialization
- **Date:** 2026-11-16
- **Status:** Accepted
- **Context:** Widgets can be started/stopped from startup recovery, UI actions and window-close notifications. Concurrent or invalid operations could double-start a widget or leak resources.
- **Decision:**
  - `WidgetInstanceState` is `Created → Initializing → Initialized → Starting → Running → Stopping → Stopped → Disposed`, plus `Faulted` and `Unavailable`.
  - Every instance owns a `SemaphoreSlim`; all lifecycle operations are serialized per instance. Global start/stop is serialized separately.
  - Start and stop are idempotent in their terminal stable states; invalid transitions throw `WidgetStateException`; a `Faulted` instance must be restarted explicitly.
  - A fresh `IWidget`, `WidgetContext` and scheduler scope are created on every start, so stopped instances hold no timers or views.
- **Consequences:** Predictable concurrency and resource ownership. Restart is explicit rather than implicit retry.

## ADR-0026: Isolate widget failures and never delete configuration on a failed stop
- **Date:** 2026-11-16
- **Status:** Accepted
- **Context:** One broken widget must not crash the app. Deleting a row after a failed stop could leave an orphaned running widget or lose recoverable configuration.
- **Decision:**
  - A failing initialize/start/stop/settings update marks only that instance `Faulted`, records the error and releases resources where possible; other instances continue.
  - `StartAllAsync` collects failures in `WidgetStartupReport` instead of throwing.
  - Creation persists the row before starting. If startup/window creation fails, the row and JSON are preserved and a controlled `WidgetLifecycleException` reports the instance id.
  - `DeleteAsync` stops first; if the stop fails, the persisted row is kept.
  - Only instance-store failures (database unavailable) are global `WidgetRuntimeException`.
- **Consequences:** Recoverable diagnostics and no silent data loss. Faulted rows can accumulate until the user deletes them; that is intentional.

## ADR-0027: Runtime-owned scheduler with `PeriodicTimer` and hard limits
- **Date:** 2026-11-16
- **Status:** Accepted
- **Context:** Widget-owned timers are hard to stop, can overlap and can consume unbounded resources. The runtime must guarantee cleanup on stop.
- **Decision:**
  - Widgets schedule through `IWidgetScheduler`; the runtime creates one `WidgetSchedulerScope` per instance.
  - Each schedule is one `PeriodicTimer` loop, so callbacks never overlap. Exceptions are logged and the loop continues.
  - `WidgetSchedulerOptions` enforces a 100 ms minimum interval and 16 schedules per instance; smaller intervals are clamped and logged.
  - Stopping an instance disposes its scope and awaits every loop; the root scheduler disposes remaining scopes at host shutdown.
- **Consequences:** Deterministic resource control and no hidden timers. Widgets that need bursts must model them inside a single callback.

## ADR-0028: Window host port; runtime never references XAML
- **Date:** 2026-11-16
- **Status:** Accepted
- **Context:** Widgets must appear in independent WinUI 3 windows, but the runtime must remain UI-framework agnostic and testable without a message loop.
- **Decision:**
  - `IWidgetWindowService` lives in `OpenBar.Application.Widgets`; `WidgetWindowRequest` carries the instance id, title, geometry and running `IWidget`.
  - `WidgetWindowService` (App) marshals all operations to `DispatcherQueue`, creates one `WidgetWindow` per instance and calls `CreateView()` on the UI thread.
  - Closing a widget window notifies the runtime, which stops the instance but keeps its row.
  - Window geometry is DPI-scaled; drag/resize/snapping and multi-monitor placement are deferred.
- **Consequences:** Runtime tests use a fake window service. The App owns all WinUI types and thread affinity.

## ADR-0029: Official widgets live in `modules/` projects; clock is the reference implementation
- **Date:** 2026-11-16
- **Status:** Accepted
- **Context:** Widgets need their own views and must be addable without touching the runtime. The repository already had a `modules/` structure and ADR-0001 reserved it for official modules.
- **Decision:**
  - Add `modules/System/OpenBar.Widgets.Clock` (WinUI class library) containing `ClockWidget`, `ClockWidgetView`, settings and `ClockWidgetDefinition`.
  - Keep clock logic UI-free and create the view only in `CreateView`; the widget schedules updates through the runtime scheduler and marshals text updates to the view's dispatcher.
  - Register the definition in `App` as a `WidgetDefinition` singleton; the runtime provider discovers it.
- **Consequences:** The solution now has 17 projects after Foundation 0.4. Adding a widget means adding a module project plus one registration; no runtime change is required.

## ADR-0030: Official widgets in-process; third-party plugins out-of-process later
- **Date:** 2026-11-16
- **Status:** Accepted
- **Context:** `AssemblyLoadContext` does not provide a security boundary, so it cannot be used to claim plugin isolation.
- **Decision:**
  - Foundation 0.3 runs only official widgets in-process.
  - The contracts avoid assuming a single process (`CreateView` returns an opaque object; no DI container exposure), but no IPC/sandbox is implemented.
  - Third-party plugins will require a separate process with a controlled IPC contract in a future phase.
- **Consequences:** The current runtime is intentionally not a plugin sandbox. Documentation and code comments must not claim isolation that does not exist.

## ADR-0031: Borderless topmost tool window with Desktop Acrylic for the dock
- **Date:** 2026-11-16
- **Status:** Accepted
- **Context:** The dock must feel integrated into the desktop, stay above normal windows, avoid looking like a conventional app, and not add a taskbar/Alt+Tab entry.
- **Decision:**
  - Use `OverlappedPresenter` with `SetBorderAndTitleBar(false, false)`, `IsAlwaysOnTop`, and no resize/maximize/minimize; set `AppWindow.IsShownInSwitchers = false`.
  - On Windows 11 unpackaged WinUI, the taskbar button remains unless the window is a tool window; also apply `WS_EX_TOOLWINDOW`, clear `WS_EX_APPWINDOW` and refresh the frame with `SetWindowPos`.
  - Use `DesktopAcrylicBackdrop` for blur plus a XAML tint/gradient/border. DWM round corners where supported; fall back to a solid background when Acrylic is unavailable.
  - Do not replace Explorer or the taskbar; the dock is a normal top-level app window.
- **Consequences:** The dock is visually floating and absent from taskbar/Alt+Tab. The Win32 style step is required and documented; Material is blur/tint, not optical refraction.

## ADR-0032: Persist pinned applications as a first-class entity
- **Date:** 2026-11-16
- **Status:** Accepted
- **Context:** Pinned apps need identity, launch metadata, icon source and a user-defined order that survives restarts. Reusing `AppSetting` JSON would duplicate a configuration pipeline and make reorder/update awkward.
- **Decision:**
  - Add `PinnedApplication` (`PinnedApplications`) with target kind, launch target/arguments, resolved executable, AUMID, icon key and sort order.
  - Add `IPinnedApplicationService` with ordered CRUD and a transactional full-order reorder.
  - Generate the `DockUi` migration, adding the table plus the dock visual columns with safe defaults (so existing layout rows remain valid).
  - Discover apps from the real Start Menu (`.lnk`/`.exe`) and allow an explicit executable path; never hardcode a known-app list.
- **Consequences:** Pinned apps are queryable and reorderable without JSON parsing. The schema grows by one table and five `DockLayouts` columns; no user data is removed.

## ADR-0033: Enumerate visible windows, not processes
- **Date:** 2026-11-16
- **Status:** Accepted
- **Context:** A process can be a service/background task with no user-facing window; showing every process would clutter the dock and misrepresent running apps. Packaged apps run through different hosts.
- **Decision:**
  - Enumerate top-level windows with `EnumWindows`; require visibility, a title, no tool-window style, no DWM cloak and a resolvable process path. Exclude OpenBar and shell surfaces.
  - Read AppUserModelId best-effort from the window property store for packaged/UWP apps; use the process path for Win32 apps.
  - Match pinned entries by AUMID, resolved executable path, then file name for Windows execution aliases; group multiple windows of one process into one running tile.
  - Refresh only while the dock is visible (2 s) and never on the UI thread.
- **Consequences:** Background processes never appear. Some protected/UWP windows may lack a path/AUMID and are skipped; this is documented rather than guessed.

## ADR-0034: Pure dock geometry and auto-hide state machine
- **Date:** 2026-11-16
- **Status:** Accepted
- **Context:** Edge positioning, DPI/work-area math and auto-hide timing must be testable without creating WinUI windows or waiting on real timers.
- **Decision:**
  - `DockLayoutCalculator` receives DIP metrics, work area and DPI scale and returns a physical `DockRect`; it handles four edges, alignment, offsets, stretch and clamping.
  - `DockMonitorResolver` resolves `primary`/`index:N` and falls back to primary when a monitor disappears.
  - `DockAutoHideController` is a deterministic state machine with a leave delay and an activation-edge check; the App feeds it cursor positions from a low-frequency timer only while enabled.
- **Consequences:** Geometry/auto-hide behavior is covered by fast unit tests; the host only translates state to `AppWindow.Show/Hide`.

## ADR-0035: Application discovery and settings in a separate window
- **Date:** 2026-11-16
- **Status:** Accepted
- **Context:** The dock window is only a few dozen pixels tall; a `ContentDialog` hosted in that XamlRoot is clipped and unusable (verified during development).
- **Decision:** Keep the dock free of modal dialogs. `DockView` raises an `OpenToolsAsync` delegate; the App opens one normal `DockToolsWindow` with the application list, explicit path add, appearance settings and the test-widget action.
- **Consequences:** The tools window is usable and can appear in the taskbar normally, while the dock remains minimal. Only one tools window is kept and it is closed during shutdown.

## ADR-0036: Explicit pointer-based drag reorder
- **Date:** 2026-11-16
- **Status:** Accepted
- **Context:** `ListView` built-in reorder (`CanReorderItems`) did not start reliably in the tool-window dock, especially when the window was not focused.
- **Decision:**
  - Listen to `PointerPressed/Moved/Released/CaptureLost` with `handledEventsToo: true`, require a 6 px threshold, capture the pointer and hit-test pinned item bounds on release.
  - Move the item inside the `ObservableCollection`, which persists the order through `IDockController.ReorderPinnedAsync`.
  - Suppress the following tap after a drag so it does not launch the app.
- **Consequences:** Reorder works with real mouse input even when unfocused; unpinned running tiles are not draggable.

## ADR-0037: Use real shell thumbnails with a retryable cache
- **Date:** 2026-11-16
- **Status:** Accepted
- **Context:** Icons are central to the dock's quality, but shell thumbnail extraction can fail transiently and must not produce a permanently generic dock.
- **Decision:**
  - Load `.exe`/`.lnk` icons through `StorageFile.GetThumbnailAsync` at 2× the display size; cache successful `BitmapImage`s per path/size.
  - Evict failed/null entries and retry when an item without an icon is refreshed; use a neutral symbol only as the last fallback.
  - For shortcuts, prefer the resolved executable thumbnail when it is not a shell host; never download icons.
- **Consequences:** Real icons render at usable DPI, transient failures recover, and no external network dependency is introduced.

## ADR-0038: Theme dictionaries and honest Acrylic materials
- **Date:** 2026-11-16
- **Status:** Accepted
- **Context:** The dock must look coherent in light and dark Windows themes without claiming optical effects WinUI does not provide.
- **Decision:**
  - Keep `DesktopAcrylicBackdrop` as the real blur material and layer an XAML gradient/border/tint above it.
  - Store `Theme` (`System`/`Light`/`Dark`) and `CornerRadius` in `DockLayout`; apply `ElementTheme` on the dock root and use `ThemeDictionaries` for shell, border, tint, action, hover, fallback and running-dot brushes.
  - Expose the radius through a bound `CornerRadius` value; keep DWM round corners as a window-level fallback.
  - Describe the result as blur/tint/reflections, never as refraction.
- **Consequences:** The dock adapts to both themes without a second visual tree. Acrylic availability still depends on Windows composition and falls back to a solid window background.

## ADR-0039: Proximity magnification with fixed layout cells
- **Date:** 2026-11-16
- **Status:** Accepted
- **Context:** A single hover scale is not dock-like and can make neighbours jump or move the dock.
- **Decision:**
  - Keep each item's layout cell fixed and animate only a render transform.
  - `DockMagnificationCalculator` receives item centers along the dock axis, the cursor position, icon size, spacing and maximum magnification. It applies a smoothstep falloff within a radius based on icon+spacing.
  - `DockView` measures the rendered item centers on pointer movement and drives every `DockItemControl`; the same code handles horizontal and vertical docks.
- **Consequences:** Neighbours react proportionally to the real cursor and the dock geometry never changes during hover. Cost is bounded to a small visual-tree walk while the pointer is over the dock.

## ADR-0040: Fullscreen detection with an explicit unknown state
- **Date:** 2026-11-16
- **Status:** Accepted
- **Context:** The dock must not appear over exclusive or borderless fullscreen apps. A maximized window is not necessarily fullscreen, and the dock becoming foreground can hide the fullscreen window from a naive foreground-only check.
- **Decision:**
  - Treat `SHQueryUserNotificationState` D3D/presentation states as exclusive fullscreen.
  - Treat a foreground window that covers the entire monitor and has no caption as borderless fullscreen; maximized windows (work-area only or captioned) are not.
  - If the foreground belongs to OpenBar, return `FullscreenKind.Unknown`; `DockWindowService` keeps the previous state instead of assuming normal mode. The dock is hidden on a positive fullscreen result and restored only after the state clears.
- **Consequences:** Chrome F11 and shell fullscreen states work; custom-chrome borderless apps can be misclassified. Games were not launched for validation, so that path is documented as partially verified.

## ADR-0041: Separate auto-hide show/hide delays and interaction suppression
- **Date:** 2026-11-16
- **Status:** Accepted
- **Context:** A single hide delay is not enough to tune reveal behavior, and menus/settings disappearing under the cursor is a usability bug.
- **Decision:**
  - Persist `AutoHideShowDelayMs` and `AutoHideHideDelayMs`; the state machine uses a dwell timer at the activation edge and a separate leave timer for hiding.
  - `DockView` raises `InteractionStateChanged` for context menus; the App suppresses auto-hide while the tools window is open. Both reset the delay when interaction begins.
  - Polling runs at 120 ms only while auto-hide is enabled; no timer remains active otherwise.
- **Consequences:** Reveal/hide timing is configurable and stable, with no flicker loops. A very small activation edge remains resolution-dependent by nature.

## ADR-0042: Use the target display's DPI and persist a logical monitor selector
- **Date:** 2026-11-16
- **Status:** Accepted
- **Context:** Using the current window DPI while moving to another monitor produces wrong sizes/positions; a physical monitor id is unstable across reconnections.
- **Decision:**
  - Persist `primary`/`index:N` and resolve it against `DisplayArea.FindAll()` with a primary fallback.
  - Compute geometry from the target display's work area and DPI via `MonitorFromPoint` + `GetDpiForMonitor`, falling back to `GetDpiForWindow`.
  - Re-apply on `DisplayAreaWatcher.Updated`.
- **Consequences:** Two displays were exercised successfully (primary ↔ secondary). Mixed DPI between displays still needs hardware validation.

## ADR-0043: Respect Windows reduced-motion and expose an explicit override
- **Date:** 2026-11-16
- **Status:** Accepted
- **Context:** Animations must not ignore accessibility preferences.
- **Decision:**
  - Read `UISettings.AnimationsEnabled` and observe `AnimationsEnabledChanged`.
  - Persist a `ReduceAnimations` override. The effective duration is zero when either the system preference is off or the override is enabled.
  - The same effective duration drives item magnification and dock fade/scale transitions.
- **Consequences:** Motion can be reduced without changing layout; the override is visible in settings and testable through the persisted field.
